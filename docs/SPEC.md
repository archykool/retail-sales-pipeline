## 0. What this project is

A batch ETL pipeline that reads daily retail sales files (CSV + JSON reference data), validates every record, transforms survivors into star-schema facts, and loads them into PostgreSQL running in Docker. Invalid records are quarantined, not dropped silently.

**The real deliverable is not the code.** It is a 10-minute video in which I can point at any file and say what it does, why it exists, and what would break if it didn't. Every design decision below is chosen partly for *explainability on camera*.

## 2. Scope

### 2.1 In scope (build this)

- `PipelineConfig` reading all settings from environment variables
- CSV extractor + JSON extractor behind one abstract `Extractor` base class
- Record-level validator producing valid records **and** typed rejection reasons
- Transformer: reference-data models **and** sales measures (`gross_sales`, `discount_amount`, `net_sales`)
- Rejected-record CSV writer (local file)
- PostgreSQL loader: `stg_sales`, `dim_customers`, `dim_products`, `fact_sales`, `etl_rejected_sales`, `etl_run_log`
- `SalesPipeline` orchestrator with a **dry-run mode**
- `sql/schema.sql` (DDL) and `sql/analytics.sql` (business + reconciliation queries)
- `docker-compose.yml` for PostgreSQL, with an init script creating dev and prod databases
- A deliberately dirty demo dataset with a documented catalogue of bad rows
- A small pytest suite covering validator rules and money math
- `README.md` with run instructions

### 2.2 Out of scope (do NOT build)

State these on camera as *deliberate* exclusions — it reads as judgment, not omission.

- **No orchestrator** (Airflow, Prefect, Dagster). A cron-able `main.py` is the correct size for a daily single-file batch.
- **No ORM** (SQLAlchemy, Django). The assignment is testing SQL and OOP; an ORM hides both.
- **No cloud** — no S3, no Snowflake, no GCP, no deployment of any kind.
- **No web UI, no API, no dashboard.** Analytics are SQL files run in DBeaver/psql.
- **No SCD Type 2** on dimensions. Overwrite-on-conflict only. Noted as the obvious next step.
- **No CDC / incremental watermarks.** Idempotent full-file reload per run (§7.3).
- **No streaming, no parallelism, no async.**
- **No pydantic.** Validation is the graded artifact; it must be visible code.
- **No secrets in the repo.** `.env` is gitignored; `.env.example` is committed with placeholders.
- **No real customer data.** All demo data is synthetic and generated by a committed script.

### 2.3 Anti-goals

- One 600-line `main.py`.
- A validator that raises on the first bad row.
- `float` for money.
- Loading first and checking later. See §8.

### 3.1 Dependency rule — **import direction, not call order**

```
config ─┐
        ├─> extractors ─> validators ─> transformers ─> loaders
models ─┘
                    pipeline imports all of the above
```

Arrows point one way and describe **which module may `import` which**. `transformers.py` must not import `loaders.py`. `loaders.py` must not import `validators.py`. Only `pipeline.py` knows the whole story.

**This is deliberately not the same as runtime call order** (§7.0), where the transformer runs before the validator for reference data and after it for sales. Modules do not import each other to achieve this — `pipeline.py` sequences the calls, and every module depends only on `models.py` for its types. Say this distinction out loud in the video; it is the difference between a dependency graph and a call graph, and it is exactly what "how do the files interact" is asking about.

## 4. Data contract (`src/models.py`)

Plain `@dataclass` objects. Frozen where they represent immutable facts.

| Model | Fields | Built by |
|---|---|---|
| `RawSalesRecord` | `row_num, source_file` + all CSV columns **as `str`** | `CSVExtractor` |
| `Customer` | `customer_id, customer_name, region, signup_date, segment` | **`ReferenceDataTransformer`** |
| `Product` | `product_id, product_name, category, list_price` | **`ReferenceDataTransformer`** |
| `ValidSalesRecord` | `row_num: int, source_file: str, order_id: int, order_date: date, customer_id: str, product_id: str, quantity: int, unit_price: Decimal, discount_rate: Decimal` | `SalesDataValidator` |
| `FactSalesRecord` | `ValidSalesRecord` fields + `gross_sales, discount_amount, net_sales` (all `Decimal`) | `SalesDataTransformer` |
| `RejectedRecord` | `row_num, source_file, raw_payload: dict, reason_code: str, reason_detail: str, rejected_at` | `SalesDataValidator` |
| `PipelineResult` | `run_id, counts, duration, dry_run: bool, status` | `SalesPipeline` |

Provenance (`row_num`, `source_file`) survives validation. `stg_sales` stores both, and when the §8.2 reconciliation fails to balance they are the only way to locate the offending row in the source file. See D-020.

**Extractors never build domain objects.** `CSVExtractor` returns `RawSalesRecord` (strings). `JSONExtractor` returns `list[dict]` (raw parsed JSON). The uniform rule — *everything that comes off disk is untrusted* — is what makes the model layer a state machine rather than a bag of classes. See D-016.

**Why four sales states:** each marks a transition. Untrusted strings → proven types → computed measures. A function taking `ValidSalesRecord` cannot be handed unvalidated input, so the type signature tells you where in the pipeline you are.

## 5. Database schema (`sql/schema.sql`)

Star schema. Surrogate integer keys on dimensions, natural business keys kept as unique constraints.

```sql
CREATE TABLE IF NOT EXISTS etl_run_log (
    run_id          UUID PRIMARY KEY,
    source_file     TEXT NOT NULL,
    started_at      TIMESTAMPTZ NOT NULL,
    finished_at     TIMESTAMPTZ,
    rows_extracted  INT,
    rows_valid      INT,
    rows_rejected   INT,
    rows_loaded     INT,
    status          TEXT NOT NULL      -- RUNNING | SUCCESS | FAILED
);

CREATE TABLE IF NOT EXISTS stg_sales (
    run_id        UUID NOT NULL,
    source_file   TEXT NOT NULL,
    row_num       INT  NOT NULL,
    order_id      INT  NOT NULL,
    order_date    DATE NOT NULL,
    customer_id   TEXT NOT NULL,
    product_id    TEXT NOT NULL,
    quantity      INT  NOT NULL,
    unit_price    NUMERIC(12,2) NOT NULL,
    discount_rate NUMERIC(5,4)  NOT NULL,
    loaded_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS dim_customers (
    customer_key  SERIAL PRIMARY KEY,
    customer_id   TEXT NOT NULL UNIQUE,
    customer_name TEXT NOT NULL,
    region        TEXT NOT NULL,
    segment       TEXT,
    signup_date   DATE,
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS dim_products (
    product_key   SERIAL PRIMARY KEY,
    product_id    TEXT NOT NULL UNIQUE,
    product_name  TEXT NOT NULL,
    category      TEXT NOT NULL,
    list_price    NUMERIC(12,2),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS fact_sales (
    sales_key       BIGSERIAL PRIMARY KEY,
    order_id        INT NOT NULL UNIQUE,
    order_date      DATE NOT NULL,
    customer_key    INT NOT NULL REFERENCES dim_customers(customer_key),
    product_key     INT NOT NULL REFERENCES dim_products(product_key),
    quantity        INT NOT NULL CHECK (quantity > 0),
    unit_price      NUMERIC(12,2) NOT NULL CHECK (unit_price > 0),
    discount_rate   NUMERIC(5,4)  NOT NULL CHECK (discount_rate >= 0 AND discount_rate < 1),
    gross_sales     NUMERIC(14,2) NOT NULL,
    discount_amount NUMERIC(14,2) NOT NULL,
    net_sales       NUMERIC(14,2) NOT NULL,
    run_id          UUID NOT NULL,
    loaded_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS ix_fact_sales_date ON fact_sales(order_date);
CREATE INDEX IF NOT EXISTS ix_fact_sales_cust ON fact_sales(customer_key);

CREATE TABLE IF NOT EXISTS etl_rejected_sales (
    rejected_id   BIGSERIAL PRIMARY KEY,
    run_id        UUID NOT NULL,
    source_file   TEXT NOT NULL,
    row_num       INT  NOT NULL,
    raw_payload   JSONB NOT NULL,
    reason_code   TEXT NOT NULL,
    reason_detail TEXT,
    rejected_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**Grain statement (memorize this line):** one row in `fact_sales` = one validated order line, uniquely identified by `order_id`.

The `CHECK` constraints intentionally duplicate the Python validator. That redundancy is the point: if a `CHECK` ever fires, it means the validator has a bug.

## 6. Validation rules

Every rule gets a stable `reason_code` so rejections are groupable in SQL.

### 6.1 Required by the assignment

| Code | Rule |
|---|---|
| `MISSING_FIELD` | required field absent or empty |
| `BAD_INT_ORDER_ID` | `order_id` not an integer |
| `BAD_INT_QUANTITY` | `quantity` not an integer |
| `BAD_DATE_FORMAT` | `order_date` not `YYYY-MM-DD` |
| `BAD_DECIMAL_PRICE` | `unit_price` not a decimal |
| `BAD_DECIMAL_DISCOUNT` | `discount_rate` not a decimal |
| `QTY_NOT_POSITIVE` | `quantity <= 0` |
| `PRICE_NOT_POSITIVE` | `unit_price <= 0` |
| `DISCOUNT_OUT_OF_RANGE` | `discount_rate` outside `[0, 1)` |
| `UNKNOWN_CUSTOMER` | `customer_id` not in the customer reference set |
| `UNKNOWN_PRODUCT` | `product_id` not in the product reference set |

### 6.2 Additional edge cases (the doc invites these — free credit)

| Code | Rule | Why it matters |
|---|---|---|
| `DUPLICATE_ORDER_ID` | `order_id` already seen in this file | protects fact grain; without it revenue double-counts |
| `SCHEMA_MISMATCH` | file-level shape error: CSV header missing/extra columns, a row with more fields than the header, or reference JSON that is not an array of objects | fails the whole file fast, before row processing |
| `DATE_IN_FUTURE` | `order_date > today` | classic data-entry symptom |
| `DATE_OUT_OF_PERIOD` | `order_date` outside the month in the filename | catches a wrong file dropped in the folder |
| `DISCOUNT_EQ_ONE` | `discount_rate == 1.0` | 100% off yields `net_sales = 0`; suspicious, not free |
| `QTY_EXCEEDS_THRESHOLD` | `quantity > 1000` | outlier guard, configurable via env |
| `NON_NUMERIC_CURRENCY` | `"$19.99"` or `"1,299.00"` | most common real-world price defect |
| `KEY_NORMALIZED` | ID with leading/trailing whitespace or inconsistent casing | **cleaned, not rejected** — logged only |
| `PRICE_PRECISION` | `unit_price` has >2 decimal places | rounding policy must be explicit |

**Policy line for the video:** whitespace and letter-case on IDs are *cleaned* and logged as `KEY_NORMALIZED`; everything else is *rejected*. Cleaning a cosmetic defect is safe — stripping and upper-casing an ID cannot change *which* entity it refers to. Cleaning a semantic one — guessing at an unknown customer — is not. That boundary is the judgment call an examiner will probe.

### 6.3 Validator contract

```python
def validate(
    self, records: list[RawSalesRecord]
) -> tuple[list[ValidSalesRecord], list[RejectedRecord]]
```

Constructed with the valid ID sets derived from `Customer` / `Product` objects (§7.0). Never raises on bad data; raises only on programmer error. One record can produce **multiple** rejection reasons — collect all of them into `reason_detail`.

## 7. Transform and load behaviour

### 7.0 Pipeline execution order (the transformer runs twice)

```
1. CSVExtractor      -> list[RawSalesRecord]
2. JSONExtractor     -> list[dict] (customers), list[dict] (products)
3. ReferenceDataTransformer -> list[Customer], list[Product]
4. derive valid-ID sets from (3)
5. SalesDataValidator(id_sets) -> (valid, rejected)
6. SalesDataTransformer -> list[FactSalesRecord]
7. loaders
```

Steps 3 and 6 are both "transform". Reference data must be transformed **before** validation because the validator needs the ID sets that step 3 produces. This is the single most non-obvious thing in the design and therefore worth 20 seconds on camera: *"the transformer runs twice, and the reason is that the validator's foreign-key check depends on the transformer's output."*

No module imports another to achieve this. `pipeline.py` sequences it. See §3.1.

### 7.1 Money math

```
gross_sales     = quantity * unit_price
discount_amount = gross_sales * discount_rate
net_sales       = gross_sales - discount_amount
```

All `Decimal`. Round **once**, at the end, `ROUND_HALF_UP`, to 2dp. Do not round intermediates — rounding `discount_amount` before subtracting reintroduces the error `Decimal` was chosen to avoid.

### 7.2 Dimension loading

Dimensions load **before** the fact table. Upsert:

```sql
INSERT INTO dim_customers (customer_id, customer_name, region, segment, signup_date)
VALUES (%s, %s, %s, %s, %s)
ON CONFLICT (customer_id) DO UPDATE
SET customer_name = EXCLUDED.customer_name,
    region        = EXCLUDED.region,
    segment       = EXCLUDED.segment,
    updated_at    = now()
RETURNING customer_key;
```

Then build in-memory maps `{customer_id: customer_key}` and `{product_id: product_key}` and resolve fact rows through them. That dictionary is the entire surrogate-key mechanic.

### 7.3 Idempotency

Running the same file twice must not double revenue. Per run:

1. `DELETE FROM stg_sales WHERE source_file = %s`
2. `DELETE FROM fact_sales WHERE order_id IN (...)` for this file's order IDs
3. `DELETE FROM etl_rejected_sales WHERE source_file = %s`
4. Insert everything fresh

Dimensions are upserted, never deleted.

**Acceptance test: run `main.py` twice, confirm `SELECT SUM(net_sales) FROM fact_sales` is identical.** Demo this live — it is the most convincing 15 seconds available.

### 7.4 Transaction boundary

One transaction for the entire load. `DatabaseConnection` is a context manager: commit on clean exit, rollback on exception, always close.

### 7.5 Insert strategy

`executemany` / `execute_batch` in chunks (default 1000).

## 8. Correctness strategy

The PDF's checkpoint box asks two questions directly. Answer both explicitly.

### 8.1 "Can you check output before loading into Postgres?"

**Dry-run mode.** `python main.py --dry-run` runs extract → transform(ref) → validate → transform(sales), writes the rejected CSV and `data/rejected/preview_fact_sales.csv`, prints the summary, and **opens no database connection at all**.

**Environment separation.** Two databases, `sales_dev` and `sales_prod`, created by `docker/initdb/01_create_databases.sql`. Load to dev, verify, repoint `DB_NAME`, load to prod. Same code, different config — which is why `PipelineConfig` reads the environment.

> Note: a single container's `POSTGRES_DB` variable creates only **one** database. The second one requires the init script above, mounted at `/docker-entrypoint-initdb.d/`. Init scripts run only on first volume creation — `docker compose down -v` is required to re-trigger them.

Dry-run proves the *logic*; the dev database proves the *load*. They catch different failures. Say that distinction out loud rather than claiming dry-run covers everything.

### 8.2 "How do you know the answer is correct?"

Four independent checks:

1. **Row conservation.** `rows_extracted == rows_valid + rows_rejected`, and `rows_valid == COUNT(*) FROM stg_sales` for this run.
2. **Control totals.** `SUM(net_sales)` computed in Python during transform vs. `SELECT SUM(net_sales) FROM fact_sales WHERE run_id = ...`. Must match to the cent. Catches type-coercion bugs at the DB boundary that row counts cannot.
3. **Hand-checked golden rows.** Three rows computed manually in the README (e.g. `qty=4, price=25.00, discount=0.10 → gross 100.00, discount 10.00, net 90.00`), asserted in `tests/test_transformers.py`.
4. **Referential integrity.** `LEFT JOIN` from `fact_sales` to each dimension returns zero orphans.

Plus the negative check: **every source row appears either in `fact_sales` or in `etl_rejected_sales`, never both, never neither.**

```sql
SELECT
    (SELECT COUNT(*) FROM stg_sales          WHERE run_id = :run) AS staged,
    (SELECT COUNT(*) FROM fact_sales         WHERE run_id = :run) AS facts,
    (SELECT COUNT(*) FROM etl_rejected_sales WHERE run_id = :run) AS rejected;
```

Put these in `sql/analytics.sql` under `-- RECONCILIATION` and run them on camera.

Two artifacts, written in this order:

1. `docs/bad_records_catalogue.md` — the oracle. One row per planted defect with
   `row_num`, the defect, and the expected `reason_code`. Includes the precedence
   rules that decide the primary code when a row breaks several rules at once (D-021).
2. `scripts/generate_demo_data.py` — implements the catalogue. 200 sales rows,
   20 customers, 15 products.

**Catalogue first, generator second, and both before the validator.** If the
generator is written first the catalogue becomes a transcript of its output and can
no longer disagree with it. Written first, the catalogue is a specification the
generator implements — and the disagreements are the signal. See D-012.

Built fifth rather than second because the catalogue's row numbers are quoted by the
extractor tests, so it only had to precede Step 4, not Step 3.

**Exit:** three files in `data/raw/`; catalogue covers every row-scoped code in §6
(`SCHEMA_MISMATCH` is file-scoped and is exercised by an extractor test fixture in

**Commit:** `feat: bad-record catalogue and synthetic demo data` ✅

### Step 5 — Validator

### Step 13 — Analytics and reconciliation SQL
**PDF anchor:** Step 13 — "Run Analytics Queries", whose only instruction is "should

`sql/analytics.sql`, one commented block per business question: revenue by day, top
products by revenue, revenue by region, highest-lifetime-value customer, rejected
records by `reason_code`. Plus the `-- RECONCILIATION` block from §8.2.

The reconciliation block also asserts `SUM(gross) - SUM(discount) - SUM(net)`, whose
expected value is **-0.03**, not zero (D-024) — with a comment saying so and why.
Demonstrating a predicted non-zero is stronger than demonstrating a zero: a zero can
come from two errors cancelling or from a check that is not running.

Plus a `-- PREVIEW COMPARISON` block, which mirrors `preview_fact_sales.csv` column for
column so the dry-run artifact and the loaded table can be read side by side:

```sql
-- PREVIEW COMPARISON: mirrors preview_fact_sales.csv column for column.
-- The two joins ARE the surrogate-key mechanism, made visible: natural keys are
-- swapped for integer keys at load time (§7.2) and swapped back at query time.
-- Nothing else in the project shows both halves of that trade in one statement.
SELECT c.customer_id, p.product_id, f.order_id, f.order_date,
       f.quantity, f.unit_price, f.discount_rate,
       f.gross_sales, f.discount_amount, f.net_sales
FROM fact_sales f
JOIN dim_customers c USING (customer_key)
JOIN dim_products  p USING (product_key)
ORDER BY f.order_id;
```

The join is not a workaround for the preview's column substitution — it is the thing worth
showing. D-005's cost ("`fact_sales` shows `product_key = 7`, not `SKU-1042`") and its
mechanism are the same two lines.

**Exit:** every query returns plausible non-empty results.
**Commit:** `feat: analytics and reconciliation queries`

## 14. Windows notes

Developed on Windows, graded elsewhere. These are real, not theoretical.

| Issue | Requirement |
|---|---|
| CSV blank lines | Always `open(path, "w", newline="", encoding="utf-8")`. Without `newline=""`, `csv.writer` emits `\r\r\n` on Windows and every record is followed by a blank row. |
| Line endings in git | `.gitattributes` with `* text=auto eol=lf`. Committed in Step 1. |
| Exit codes | Bash `echo $?` → PowerShell `$LASTEXITCODE`, cmd `%ERRORLEVEL%`. |
| Paths | `pathlib.Path` everywhere. No string concatenation, no hardcoded `\` or `/`. |
| Virtualenv | `python -m venv venv` then `venv\Scripts\activate`. |
| Postgres port clash | If a native PostgreSQL is installed locally it already holds 5432. Map the container to `5433:5432` and set `DB_PORT` accordingly rather than uninstalling anything. |
| Docker init scripts | Run only on first volume creation. Changing `01_create_databases.sql` requires `docker compose down -v`. |
